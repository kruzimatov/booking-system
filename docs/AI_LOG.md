# AI usage log

The project was built with an AI coding assistant (Claude Code), one phase at a time, following [PLAN.md](PLAN.md) and the rules in [CLAUDE.md](../CLAUDE.md). Every phase ended with linting, type checks, the full test suite and a manual run against the real API or the browser.

This log lists moments where the generated result was wrong or incomplete, how it was caught, and what changed. They are the reason every step was verified instead of trusted.

| Phase | What was produced | How it was caught | What changed | Why it matters |
|---|---|---|---|---|
| Planning | First plan locked booking rows (`SELECT ... FOR UPDATE`) to stop double booking | Review of the plan before any code | Lock the specialist row; PostgreSQL exclusion constraints became the real guarantee. 33 more plan issues fixed (timezones, buffers, orphaned bookings, tests that would not test the constraints) | When a slot is free there is no booking row to lock, so two requests would both insert |
| 1 | Autogenerated migration for `users` | Every test failed: `check constraint "ck_users_user_role" already exists` | Edited the migration by hand to declare the role check once | Autogenerate emitted the same CHECK constraint twice for an Enum column; migrations are now always read before applying |
| 1 | API docs at `/docs` | Checked against the nginx design | Moved docs to `/api/docs` | nginx only forwards `/api` to the backend, so `/docs` would have been unreachable in production |
| 1 | Token expiry left to PyJWT's own check | Design review of how tests control time | Expiry checked against the injected clock | PyJWT uses the real clock, so time-based tests (expired token, cancellation cutoff) could not be exact |
| 2 | Autogenerated `services` migration with `%` in CHECK constraints | Migration failed: `operator does not exist: integer %% integer` | Constraints use `mod()` in both the model and the migration | Alembic escaped `%` as `%%` in the rendered SQL |
| 2 | Service create and update returned the price as sent (`150000`) | API test expected `150000.00` | Prices normalized to two decimals in the schema | Reads from the database returned `150000.00`, so the same field had two formats |
| 3 | Scheduling migration and slot engine | 100% line coverage on the pure engine; lunch break, buffer, time off and timezone cases checked one by one | None needed in the engine | The engine is the single rule for "is this time free", so it was tested first and in isolation |
| 4 | Bookings migration | Same duplicate CHECK problem on `status` | Fixed by hand; exclusion constraints and `btree_gist` added manually | Alembic cannot model `EXCLUDE` constraints |
| 4 | Test expecting 09:00 to stay free before a 10:00 booking | The test failed, the engine did not | Test corrected: with a 15-minute buffer, 09:00 blocks until 10:15 | Confirms the rule "your own buffer may not run into the next booking" |
| 4 | Concurrency tests | Run 20 times in a row, all passed | None | A race test that passes once is not proof; repeated runs show it is not flaky |
| 5 | Status change returned the booking's history without the new event | API test on the admin cancel response | Reload the booking after commit | The event list was loaded before the change and returned stale |
| 5 | Lifecycle tests moved the frozen clock forward by hours | Tests returned 401 | Longer-lived test tokens in those tests | Moving time also expired the test login; the application was correct |
| 6 | Frontend written for Mantine v8 and the Vite template's TypeScript 6 | TypeScript build errors | `Grid gutter` renamed to `gap` (Mantine v9); TypeScript pinned to 5.9 for the OpenAPI type generator | Library versions were newer than assumed; the compiler, not guesswork, decided |
| 6 | Generated types marked `allowed_actions` as optional | TypeScript errors in the frontend | Backend response schemas now mark defaulted fields as required in OpenAPI | Fixed at the source instead of adding `?.` checks everywhere in the UI |
| 6 | Booking wizard | Browser check: slot taken while on the confirm step | Verified: message, fresh times, user returns to the time step | The most important client edge case, checked end to end in a real browser |
| 7 | nginx rate limiting | Burst of login attempts against the running stack | Verified `429 RATE_LIMITED` after 10 attempts, normal API unaffected | Behind the host proxy, limits must use the real client IP (`real_ip`), or every visitor would share one limit |
